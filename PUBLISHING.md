# PR из админки и публикация после merge

## Первичная настройка

Репозиторий: `hellhoundisalab/shomei`, публичный, основная ветка `main`.
Первый коммит содержит сборщик, workflows и пустой каталог; фотографии и заявки
из dev-стенда автоматически не переносятся. Секреты, `.preview-qa` и дизайн-экспорты
в репозиторий не входят.

1. В Settings → Actions → General включить **Allow GitHub Actions to create and
   approve pull requests**. Workflow использует это разрешение только для создания PR.
2. Создать fine-grained PAT: только этот репозиторий, Actions **read/write**,
   Contents **read**, Pull requests **read**. Это отдельный доступ, не OAuth админов.
   Сохранить локально в игнорируемом `pgallery_bot/.env.dev`:

   ```dotenv
   DEV_GALLERY_REPOSITORY=hellhoundisalab/shomei
   DEV_GALLERY_DISPATCH_TOKEN=значение_токена
   ```

   Пересоздать только review: `python scripts/dev.py up` запускает весь dev-стенд;
   для точечного обновления использовать `compose up -d --no-deps --build review`
   через существующий helper `scripts/dev.py` с `compose.dev.yaml` и `.env.dev`.
   В production нужны `GALLERY_REPOSITORY`, `GALLERY_DISPATCH_TOKEN` и ровно та же
   версия пакета `gallery_build`, что в `main` галереи. Production-образ бота пока
   этот пакет не включает: текущая интеграция подключена только в dev Compose.
   При переносе токен хранить в repository secret приватного бота и доставлять
   существующим механизмом секретов деплоя; в публичную галерею PAT не класть.
3. В Settings → Pages выбрать **GitHub Actions**. В environment `github-pages`
   разрешить deployment только из `main`.
4. Защитить `main`: require pull request, require status check **build**, require
   branch to be up to date, без обхода правил ботом. Автоматизация никогда не пишет
   в `main`; защита дополнительно закрывает прямые push людей. На личном репозитории
   с единственным разработчиком обязательный внешний review включать необязательно.
5. Когда готовы к публичному выпуску, задать repository variable **PAGES_ENABLED=true**.
   После следующего merge в main успешный build запустит Pages. Пока переменная не
   задана, выполняются только проверки. Custom domain/DNS `shomei.ru` подключаются
   отдельно в Pages; исходники используют относительные ссылки и работают также
   под стандартным адресом `https://hellhoundisalab.github.io/shomei/`.

Все workflow actions закреплены на commit SHA. `requirements-ci.txt` фиксирует
версии Python-зависимостей; `uv.lock` использует публичный PyPI.

## Работа администратора

1. Принять выставку; сохранить текст, оформление и EXIF. Нужны публичные HTTPS
   web-копии и превью S3. Ссылки локального RustFS (`s3.localhost`) отправить нельзя.
2. Нажать **Подготовить PR**. Панель читает точный SHA `main`, существующий каталог
   и ручной `custom.css`. Добавляет только выбранную выставку, строит обе страницы
   и сохраняет закрытый ZIP. Новая выставка — первая; правка существующей сохраняет
   её позицию в публичном каталоге. Обычный локальный предпросмотр устроен иначе:
   он показывает принятые локальные заявки и ставит выбранную первой.
3. В меню предпросмотра после проверки нажать **Создать PR**. Админка проверяет
   актуальность заявки, renderer и `main`, отправляет фиксированный workflow_dispatch.
   В input только публичный manifest и хеши, максимум 48 КБ; приватных фото, S3-ключей,
   admin URL, Telegram ID и произвольных файлов нет. Доступ GitHub к домашней сети
   или bridge endpoint не требуется.
4. **Обновить статус** покажет ссылку на run/PR. Actions воспроизводит полный сайт
   и сравнивает SHA-256 файлов с согласованным предпросмотром. Только после проверки
   отдельная job с короткоживущим `GITHUB_TOKEN` создаёт два файла в ветке
   `publish/<id>/<revision>`: manifest выставки и catalog.json. Ветки не force-push'атся.
5. Проверить PR в GitHub. При необходимости нажать **Approve workflows to run**:
   GitHub может требовать это для PR, созданных `GITHUB_TOKEN`. Workflow PR строит
   artifact `gallery-pr-preview`, без production-секретов и deploy. Ручные правки
   делать в этой ветке; CI должен заново пройти. Повтор кнопки в админке возвращает
   существующий PR и не затирает ручные изменения. Локальный согласованный preview
   относится к исходному автоматическому коммиту; после правок проверять новый CI artifact.
6. Вручную merge → push `main` → build итогового SHA → Pages (если включён).
   Artifact PR не используется для production. `release.json` содержит commit/run_id.
   Админка различает «PR объединён» и подтверждённую публикацию: автоматическая сверка
   deploy и уведомление автора пока не реализованы.

## Повторы и ограничения

- Двойной клик блокируется в UI, общим maintenance lock и записью попытки в приватном
  generated S3 до dispatch. При неопределённой сетевой ошибке повтор разрешён через
  120 секунд. Ветка и job ID детерминированы; повтор run возвращает существующий PR,
  включая closed/merged. После сбоя между созданием ветки и PR можно повторить run.
- Одна глобальная concurrency group Actions. GitHub может заменить ожидающий run
  более новым; состояние/отмена видны в Actions, доступен повтор. Это не надёжная FIFO
  очередь. При текущей небольшой нагрузке стартуем так; worker/outbox — следующий этап.
- Если `main` изменился, нужно заново нажать «Подготовить PR». При подготовке проверяется
  совпадение всех файлов renderer с репозиторием; локальные правки шаблонов сначала
  должны попасть в main отдельным PR. Переводы строк Windows/Linux нормализуются.
- Для одной выставки одновременно допускается один открытый автоматический PR.
  Закрытый PR автоматически не открывается заново. Измените данные/базу и соберите
  новую ревизию либо вручную reopen существующий PR.
- Ручной CSS сохраняется; произвольный HTML/JS или ZIP назад в админку ещё не импортируется.
- Фотографии пока адресуются существующими публичными S3 keys, не копируются в Git.
  Хеш сайта фиксирует ссылки, **не байты внешних фото**. Immutable media snapshots,
  отзыв уже открытого PR при удалении заявки и защита от повторной публикации удалённого
  материала — незакрытые задачи до полноценного публичного запуска. Перед merge после
  удаления/изменения материалов администратор обязан закрыть устаревший PR.
- Статус ищет последние 100 workflow runs. Старые ошибки смотреть в GitHub; PR ищется
  по точной ветке. История приватных ZIP автоматически не чистится.

## Проверка

`python -m unittest discover -s tests` проверяет допустимые пути, закрытые адреса,
повторы/closed PR, восстановление после частичного сбоя, ручные изменения ветки,
каталог, CSS и точность preview. Интеграционный тест панели находится в
`pgallery_bot/tests/test_gallery_publication.py`; внешние API в нём подменены.
Реальная проверка от кнопки до PR требует PAT и публичных S3-копий принятой выставки.
